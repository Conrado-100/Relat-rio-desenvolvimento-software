01 · Fundamentos de Engenharia de Software

Comece entendendo o produto e o processo antes de falar de ferramentas.

Aula 1

O que é software?

Software não é apenas o código: o material fornecido o apresenta como programa de computador + documentação associada, com determinada funcionalidade.

Software genérico

É desenvolvido para atender uma classe de usuários ou necessidades. Exemplos do material: processadores de texto, editores de imagem, bancos de dados e sistemas de controle de estoque.

Software personalizado

É desenvolvido para uma necessidade mais específica. Exemplos do material: sistemas de escritórios de advocacia, tribunais, softwares policiais e jogos.

Ideia-chaveO usuário não precisa conhecer a implementação interna. Ele precisa conseguir realizar seu objetivo com o sistema.
Identifique o problema

Qual necessidade o software deve resolver?

Identifique o usuário

Quem utilizará a solução e quem mais será afetado por ela?

Defina a funcionalidade

O que precisa acontecer para que a necessidade seja atendida?

Aula 2

Engenharia de Software e processo de software

O material define Engenharia de Software como a disciplina da engenharia preocupada com os aspectos da produção de software.
Visão geral: especificar → desenvolver → validar → evoluir.
Aula 3

Conceitos de produto: MVP, KISS e Happy Path

MVP

Minimum Viable Product: versão simples e funcional do software capaz de resolver a dor principal do usuário. A ideia é entregar algo utilizável cedo e aprender com o uso.

KISS

Keep It Simple, Stupid: priorize simplicidade. Evite complexidade que não seja necessária para resolver o problema.

Happy Path

É o caminho de cenário ideal, em que tudo ocorre conforme esperado. Ele é útil como referência, mas não representa os erros, exceções e situações reais do sistema.

Aula 4

Stakeholder, usuário, UI, UX e GUI

Usuário × Stakeholder

Usuário é quem utiliza o sistema. Stakeholder é qualquer parte interessada no sistema. Assim, um usuário é um stakeholder, mas um stakeholder pode não utilizar diretamente o software.

UI × UX × GUI

UI é a interface e seus elementos visuais; UX é a experiência global, fluxos e facilidade para atingir objetivos; GUI é a interface gráfica do usuário.

CMD / Terminal: interface textual em que comandos são digitados. É importante para automação, servidores e ferramentas de desenvolvimento.

02 · Engenharia de Requisitos e Modelagem

A etapa em que uma necessidade vira algo que a equipe consegue entender, discutir, modelar e validar.

Aula 1

Elicitação → análise → especificação → validação

O material apresenta especificação de software (ou engenharia de requisitos) como o processo de identificação das necessidades do sistema e divide sua especificação em elicitação/análise, especificação e validação.

O processo de requisitos é iterativo: novas informações podem gerar revisões.
Prepare a entrevista

Tenha uma pré-seleção de ideias ou hipóteses para validar, em vez de assumir que já sabe tudo.

Converse e demonstre

Converse com o cliente e, quando possível, mostre um exemplo/protótipo para descobrir o que realmente é desejado.

Analise e registre

Transforme respostas em requisitos claros, sem depender de memória informal.

Valide

Volte ao cliente para confirmar que o documento corresponde ao sistema necessário.

Aula 2

Requisitos de usuário e requisitos do sistema

TipoFocoExemplo
Requisito de usuárioNecessidade expressa do ponto de vista de quem usa/precisa do sistema.“Como cliente, quero acompanhar meu pedido.”
Requisito do sistemaForma mais detalhada e técnica do comportamento esperado.“O sistema deve exibir status, data e histórico do pedido.”
Validação de requisitosNo material, essa etapa serve para descobrir e corrigir erros no documento de requisitos. O foco é verificar se o que foi definido corresponde ao que o cliente deseja e necessita.
Aula 3

UML e diagrama de casos de uso

Em casos de uso, a fronteira do sistema delimita o que é representado como parte dele; isso não é sinônimo de “escopo do projeto”.
Conexão com MVP: nas anotações, a funcionalidade crítica do MVP pode ser destacada no diagrama de casos de uso para deixar visível o que precisa ser entregue primeiro.
Aula 4 • Prática

Transformando uma entrevista em caso de uso

Frase do cliente

“Quero vender produtos e acompanhar o pedido.”

Identifique os atores

Cliente, atendente, administrador ou outros envolvidos — conforme o sistema estudado.

Liste objetivos

Comprar produto, consultar pedido, cadastrar usuário, etc.

Desenhe a fronteira

Coloque os casos de uso dentro do sistema e os atores fora dele.

Valide com o stakeholder

Pergunte: “É exatamente isso que você espera que aconteça?”

03 · Modelos de Processo, Prototipação e Agile

Agora você decide como o trabalho será organizado e como as entregas serão feitas.

Aula 1

Modelo em Cascata × Desenvolvimento Incremental

Cascata

O material descreve o modelo como dividido em fases, com plano de atividades antes da programação. O resultado de cada etapa é uma série de documentos aprovados, e a fase seguinte deveria iniciar após a anterior.

Incremental

Começa com um protótipo ou versão inicial, recebe feedback e evolui em várias versões. Desenvolvimento e validação se alternam; o material relaciona esse modelo ao desenvolvimento ágil.

O material destaca que o incremental facilita feedback, reduz custo de mudanças e permite entrega antecipada do MVP.
Aula 2

Prototipação e Entrega Incremental

Prototipação

Um protótipo é uma versão inicial do sistema. Pode ser usado enquanto outras versões são desenvolvidas e geralmente envolve uma GUI. O processo se encerra com a avaliação do protótipo.

Entrega incremental

Pequenas partes do sistema são entregues ao cliente para uso e validação. Os incrementos podem ser telas, tabelas de banco ou funcionalidades.

Por que isso ajuda?Quanto mais cedo o cliente vê algo funcionando, mais cedo o time descobre se está seguindo a direção desejada.
Aula 3

RUP, integração/configuração e ferramentas de desenvolvimento

RUP — Rational Unified Process

No material, RUP é apresentado como um processo que reúne elementos dos modelos Cascata, Incremental e Integração/Configuração. Ele ajuda a organizar disciplinas, papéis e iterações de um projeto.

Integração e configuração

Software frequentemente reaproveita código e componentes existentes. O material cita standalone, libraries e web services como tipos envolvidos nesse reaproveitamento.

Modelagem gráfica

Ferramentas podem apoiar a criação de modelos e diagramas.

Geração / tradução

Ferramentas podem gerar código a partir de modelos e traduzir linguagens de programação.

Depuração / GUI

Ferramentas também ajudam na depuração de programas e na geração de interfaces gráficas.

Como estudar esse tópicoPense nas ferramentas como apoio ao processo: elas não substituem requisitos, arquitetura, validação ou decisões da equipe.
Aula 4

Agile, Scrum, backlog e sprint

Representação didática das relações entre backlog, planejamento, sprint, daily e revisão.

Backlog

Lista priorizada do trabalho que pode ser desenvolvido.

Sprint

Período de trabalho focado em um conjunto de objetivos e entregas.

Daily / Stand-up

Reunião frequente do time para alinhar andamento, impedimentos e próximos passos.

Referência das anotações: o exemplo de Agile usa ciclos de aproximadamente 2 semanas; na prática, a duração depende do processo adotado pela equipe.
Aula 5

Story Points e Fibonacci

SPInterpretação das anotaçõesExemplo
1Tarefa extremamente simples e rápida.Alterar a cor de um botão.
2–3Complexidade baixa a média.Tela de login simples.
5–8Demanda moderada, com regras de negócio ou integrações.Fluxo envolvendo serviços.

Atenção: Story Point não é “hora de trabalho”. É uma medida relativa de tamanho, complexidade e incerteza para comparar demandas.
Aula 6 • Prática

Montando uma sprint de exemplo

1. Comece pelo backlog

Liste tudo o que o produto precisa.

2. Priorize

Coloque primeiro o que gera valor e reduz incerteza.

3. Estime

Atribua Story Points usando uma escala relativa como 1, 2, 3, 5, 8, 13, 20.

4. Quebre itens grandes

Uma história de 20 SP pode indicar que existe trabalho demais ou incerteza demais.

5. Planeje e execute

Escolha o conjunto possível para a sprint e acompanhe diariamente.

04 · Desenvolvimento, Arquitetura e Validação

Depois de saber o que fazer e como organizar, é hora de construir e testar.

Aula 1

Definição da stack e padronização

Linguagem / Framework

Escolha a tecnologia necessária para implementar as funcionalidades.

Banco de dados

Defina o SGBD e as convenções que todos do projeto utilizarão.

Ambiente / Nuvem

Padronize ferramentas, IDEs, plugins e serviços como infraestrutura de nuvem quando aplicável.

Padronizar o ambienteA anotação destaca a necessidade de definir o que toda a equipe utilizará (sistema operacional, IDE, plugins e SGBD), reduzindo diferenças desnecessárias entre ambientes.
Aula 2

Arquitetura: como as partes do sistema se organizam

MVC é um modelo de organização. Serviços, APIs externas, mensageria e segurança podem fazer parte de arquiteturas reais mais amplas.

API externa

Integração com outro sistema por uma interface de comunicação definida.

Mensageria

Permite trocar mensagens entre partes do sistema, inclusive desacoplando produtores e consumidores.

Segurança

Deve atravessar a arquitetura: identidade, acesso, dados e integrações precisam ser considerados.

Aula 3

Boas práticas de desenvolvimento

Clean Code / Code Style

Estruture o código para que outras pessoas consigam entender e manter o sistema.

Git / GitHub Workflow

Versione o trabalho, revise alterações e mantenha um fluxo de colaboração consistente.

GitHub Actions

Automatize tarefas do processo, como validações, testes e pipelines definidos pela equipe.

Padrões de commit

Mensagens consistentes ajudam a entender o histórico e facilitam a rastreabilidade das mudanças.

Cobertura de testes

Indica quanto do código está sendo exercitado por testes; não substitui qualidade dos cenários.

Refatoração

Alterar a estrutura interna para facilitar leitura e manutenção, mantendo o comportamento externo observável.

Aula 4

Validação e estratégia de testes

O material orienta que validação envolve testar o programa por simulações, usar testes pequenos e independentes e, em softwares personalizados, considerar dados reais para testes.

Pirâmide didática: use testes unitários pequenos e rápidos em grande quantidade, complementados por integração e cenários mais amplos.

Unitário

Foca uma função, classe ou unidade pequena. Ex.: validação de cadastro de usuário.

Integração

Verifica a comunicação entre componentes, como aplicação + banco ou serviço + API.

Performance / Carga

Avalia como o sistema se comporta sob diferentes níveis de uso e carga.

Aula 5

Mocks e testes isolados

MockÉ um componente falso controlado que imita o comportamento de uma dependência real, como banco, API externa ou arquivo. Ele permite testar uma unidade sem depender da infraestrutura real.
Escolha a unidade

Ex.: serviço de cadastro.

Identifique a dependência

Ex.: banco de dados.

Substitua por mock

Defina a resposta esperada da dependência.

Execute o teste

Verifique apenas o comportamento da unidade testada.

05 · Evolução, Manutenção, Dados e Segurança

O software foi entregue. Agora começa outra etapa importante: manter, corrigir, proteger e evoluir.

Aula 1

Evolução e manutenção

No material, evolução envolve manutenção e adição de novas funcionalidades. O software é mais fácil de modificar do que hardware, mas mudanças aumentam custos.

Correções e novas funcionalidades alimentam ciclos de mudança e nova validação.
Aula 2

Bibliotecas obsoletas e “deprecated”

Por que bibliotecas ficam obsoletas?

Nas anotações, o principal motivo destacado é a descoberta de vulnerabilidades e problemas de segurança. Também pode ocorrer evolução da tecnologia, substituição por soluções mais atuais ou perda de suporte.

O que significa “deprecated”?

É uma indicação de que determinada API, biblioteca, recurso ou abordagem não deve ser adotada em novos desenvolvimentos e pode ser substituída/removida em versões futuras.

Passo a passo ao encontrar um recurso deprecated: descubra por que ele foi descontinuado → consulte a alternativa indicada → avalie impacto → migre → rode testes → remova dependências antigas.
Aula 3

Hard Delete × Soft Delete

A escolha depende do objetivo do dado, histórico, auditoria, recuperação e requisitos de retenção.
AspectoHard DeleteSoft Delete
Operação típicaDELETEUPDATE
RegistroRemovidoPermanece marcado como excluído/inativo
RecuperaçãoDepende de backup/outros meiosMais simples
ConsultasNão há dado ativo depois da remoçãoÉ necessário filtrar registros inativos quando apropriado
HistóricoPode ser perdidoPode ser preservado
Aula 4

Logs, auditoria e rastreabilidade

Para logs, a anotação diferencia o tratamento de dados operacionais: o histórico de eventos, acessos ou erros deve ser tratado com uma política de retenção. Um padrão apresentado nas notas é não usar soft delete para logs e realizar limpeza automatizada por tempo, conforme política definida.

Log

Registro de um evento: acesso, erro, ação, alteração, comunicação etc.

Auditoria

Capacidade de reconstruir o que ocorreu e acompanhar alterações relevantes.

Rastreabilidade

Ligação entre requisito, alteração, teste, versão e comportamento entregue.

Aula 5

PII, LGPD, NDA e Encoding

PII

Personally Identifiable Information: informações que podem identificar uma pessoa direta ou indiretamente. Nas anotações aparecem CPF, RG e e-mail como exemplos.

LGPD

Lei Geral de Proteção de Dados. Ao lidar com informações pessoais, o sistema precisa respeitar as regras aplicáveis de tratamento, segurança, acesso e retenção.

NDA

Non-Disclosure Agreement: acordo de confidencialidade usado para limitar divulgação de determinadas informações.

Encoding

Forma de representar caracteres em bytes. A codificação correta evita problemas de acentuação e compatibilidade, inclusive em conteúdos como pt-BR e pt-PT.

Aula 6

Software off-the-shelf e teste beta

Off-the-shelf / COTS

Software comercial pronto para uso, comprado ou assinado em vez de desenvolvido de forma totalmente personalizada. O material cita exemplos como Microsoft 365, Google Workspace, Salesforce e plataformas prontas.

Teste beta

Um grupo menor de pessoas utiliza o software antes de uma disponibilização mais ampla para identificar problemas e fornecer avaliações/feedback.

Projeto final sugerido

Construir um pequeno sistema aplicando os 5 módulos

Módulo 1 — problema

Escolha uma dor real e defina usuário, stakeholders e MVP.

Módulo 2 — requisitos

Faça entrevista, escreva requisitos, crie user stories e um diagrama de casos de uso.

Módulo 3 — processo

Escolha um modelo de desenvolvimento, monte backlog, estime Story Points e planeje uma sprint.

Módulo 4 — implementação

Defina stack, arquitetura, versionamento, testes unitários, integração e mocks.

Módulo 5 — evolução

Defina política de manutenção, logs, tratamento de dados, dependências, segurança e auditoria.
